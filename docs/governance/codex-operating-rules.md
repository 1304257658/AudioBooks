# Codex 项目操作准则

本文件是 AudioBooks 项目后续 Codex 操作的长期准则。仓库根目录的 `AGENTS.md` 是 Codex 自动发现这些规则所需的机器入口；除该入口外，所有 Markdown 文档统一存放在 `docs/`。

## 文档管理

- 所有人类可读的 Markdown 文档必须存放在 `docs/`，不得在仓库根目录或代码目录散落新增 Markdown 文档。
- 根目录 `AGENTS.md` 是唯一例外，只用于让 Codex 自动加载本准则，不作为普通项目文档维护。
- 项目说明放在 `docs/project/`。
- 工程设计与实现说明放在 `docs/engineering/`。
- 操作、协作与发布规则放在 `docs/governance/`。
- 产品审计报告放在 `docs/audit/reports/`。
- 产品审计截图、UI 树和其它证据放在 `docs/audit/evidence/<审计日期>/`。
- 移动或重命名文档时，必须同步更新仓库内的相对链接并检查引用目标存在。

## 提交规则

- Codex 完成功能修改并完成必要验证后，可以直接创建提交，不需要再次询问是否 commit。
- 每个提交只包含当前任务范围内的文件；不得顺带提交用户已有或无关的工作区变更。
- 提交信息必须说明修改结果，功能修复应引用对应审计编号，例如 `fix: resolve AUD-P0-001 first-play setup`。
- 文档、文案、测试、格式化、局部低风险修复等非重要修改，在验证通过后可以直接推送当前分支，不需要再次确认。
- 架构变更、数据迁移、安全或隐私策略、重要依赖升级、发布配置、破坏性数据操作等重要修改可以直接 commit，但 push 前必须获得用户明确确认。
- push 前必须确认当前分支、远端目标、工作区状态和待推送提交，不得推送其它分支。

## 审计分支

- `codex/audit` 是长期产品审计分支，只维护审计报告、证据、问题状态和复审记录。
- 审计分支不得实现 Android 产品功能修复；产品代码修改必须在其它分支完成。
- 审计分支产生的是文档与证据内容，完成检查后可以直接 commit 并 push。
- 每次审计开始前必须优先同步远端审计分支和最新产品代码，默认产品基线为 `origin/main`。
- 审计开始前的标准顺序是：
  1. 确认工作区干净。
  2. `git fetch origin`
  3. `git pull --ff-only origin codex/audit`
  4. `git merge --no-edit origin/main`
  5. 记录被审计的 `origin/main` 提交哈希。
- 如果用户指定其它发布分支或提交作为审计对象，以用户指定的基线为准，并在报告中明确记录。
- 如果同步失败或产生冲突，必须先解决同步问题，不得基于旧代码继续审计。

## 修复与复审

- 审计问题使用稳定编号：`AUD-P0-*`、`AUD-P1-*`、`AUD-P2-*`。
- 修复分支从最新产品开发基线创建，并在分支、提交或 PR 中引用对应审计编号。
- 修复合入产品基线后，回到 `codex/audit`，重新同步最新代码并按原用户流程复审。
- 只有在修复版本上重新走查并取得新证据后，问题才能改为“已通过”。
- 开发者说明、代码提交和自动化测试不能替代产品复审。

## 验证要求

- 修改代码时，执行与风险相称的构建、测试、静态检查和真实流程验证。
- 修改 Markdown 时，检查文档路径、相对链接、图片引用和 Markdown 结构。
- 提交前运行 `git diff --check`，并检查 `git status --short`，确认没有无关文件。
- 推送后读取远端跟踪状态，确认本地分支与远端一致。

Codex 使用根目录 `AGENTS.md` 作为项目级持久指令入口，符合[官方 OpenAI 文档](https://learn.chatgpt.com/docs/agent-configuration/agents-md)说明的仓库指令发现方式。
